# SC-832c — post-crash re-entry after a rename interruption — MANIFEST

Worker: `opus5:lexec`. **Capture only.** No arm is classified and no outcome is called
correct. This section exists because the row's empirical hold cannot be waived: the
existing L-RENTRANS rename evidence **held and then RESUMED the same process** at every
cut. It never killed the writer, never started a fresh process, and therefore observed
neither recovery nor refusal. Census and source establish the residue SHAPE and say
nothing about POST-CRASH RE-ENTRY, which is the whole claim.

## The construction

For each cut, the rename is interrupted by **SIGKILL to its whole process tree** at the
barrier, so the lifecycle descriptors are released **BY DEATH and never by a resumed
process** — that distinction is the reason this section exists. A **fresh process** is then
the only thing that touches the crashed state.

| cut | barrier | site |
|---|---|---|
| `entry` (**the control**) | `b_rn_locked_entry` | inside the two-lock region, before any check the rename then mutates |
| `tmux` | `b_rn_tmux_renamed` | after `tmux rename-session` and the main-window rename, before the state directory move |
| `dir` | `b_rn_dir_moved` | after the state directory move, before the meta rewrite |
| `meta` | `b_rn_meta_updated` | after meta `session=` is rewritten, before `workspace.md` is regenerated |

**Independence is per (cut, consumer) pair — a whole separate sandbox each, not a shared
one.** The on-disk state is additionally cloned per consumer (`clones/<consumer>/.ae`), but
**the tmux server cannot be cloned**, so a shared-server design would have let `stop`
contaminate the readers. Thirteen arms, thirteen runs.

## Preconditions, proven per arm before any fresh process starts

`death-and-descriptors.txt`, written by the check itself:

1. **the subject is dead** — `kill -0 <pid>` fails, and the remaining sandbox process list
   is recorded;
2. **the lifecycle descriptors are reacquirable** — a fresh `flock -w 2` is taken and
   released on **every** `.lifecycle.*.lock` present, and each result is recorded.

`precondition.met` is the conjunction. **`ARM-INVALID` if it is not met**, because a fresh
process that started while the writer still held a descriptor would not be re-entering a
crashed state at all. Measured: `YES` in all thirteen arms, with `rename_rc 137` (SIGKILL)
throughout.

## Ability to fail — the thread through this whole batch

**An arm that cannot observe a MIXED generation cannot support a claim that none
survives.** The identity tuple is captured from every place identity lives — tmux session
names, state directory names, meta `session=`, meta `session_id=`, `workspace.md` and its
`Session:` line, and the lifecycle lock files — at four points per arm: `1pre`, `at-cut`,
`3post-crash`, and `6after-consumer`. Whether the sources agree is **derived from the
captured row**, never asserted.

Measured across the thirteen arms: the sources **DISAGREE in 7 of 13** — every `tmux`-cut
arm and every `dir`-cut arm — and agree in the `entry` control and the `meta` cut. So the
instrument demonstrably registers a mixed generation when one is present, and the arms
that report agreement are reporting it against a recorder shown to be capable of the
opposite.

## Known limits of this section, stated

- **The clone isolates the on-disk state, not the tmux server.** A `stop` run against a
  clone still acts on the one live server. That is why every consumer gets a whole
  separate run rather than sharing one; within an arm, the tmux side is captured by the
  identity tuple before and after.
- `origin_manifest_changed_lines` compares the crashed `AE_HOME` against itself after the
  consumer ran against a **clone**, so it answers "did the consumer reach back into the
  original state", not "did the consumer mutate anything at all". The clone diff answers
  the second question.
- `ae stop` preserves session state by design, so a zero manifest delta on a stop arm is
  not evidence that nothing happened; the tuple captures the tmux side.
- Every rename here is interrupted. No arm in this section observes a rename running to
  completion; that is L-RENTRANS's `rename-effects`.
